\chapter{Conclusion and Future Work}
\label{ch:concl}

\section{Conclusion}

This thesis set out to measure, rather than assert, the workload relief that
an AI teaching assistant delivers, and to make such an assistant affordable
to operate at institutional scale. It presented a retrieval-augmented virtual
teaching assistant over NUS Canvas course materials, defined how the
instructor-hours it returns can be measured, and evaluated an extractive
retrieval-compression stage on the deployed system.

On the three research questions, the findings are as follows. For RQ1, the
thesis defines an hour-denominated measure of the instructor time an
assistant returns and identifies what the system must record to compute it:
every chat query, with its course, time, and text. The deployed system does
not yet store chat turns, so the measure is defined but not yet applied;
projected from stated assumptions, it suggests around 1.3 hours per course
per week, within a wide range of 0.1--7.2 (\autoref{eval:subsec:hours}). For RQ3, a hybrid deployment --- open-weight
models on a hosted provider for generation, with retrieval and a fallback
model kept local --- was faster than the local alternatives at equal
grounding, at a projected cost of cents per student per semester
(\autoref{eval:sec:results:providers}). For RQ2, compression cut input tokens
by half or more, and on a compute-bound local model it cut latency too; but
on the hybrid deployment its own embedding step made answers slower, and on
20 course-material questions it lowered answer quality, mainly because the
Socratic persona, given less context, more often replied with questions that
conveyed nothing (\autoref{eval:sec:results:quality}).

Two lessons cut across these results. First, the cost lever is input tokens,
but which tokens matters: on this system, the tool definitions and system
prompt sent with every agent pass outweigh the retrieved context that the
compression literature targets (\autoref{design:subsec:tokenaudit}). Second,
what a deployed assistant can later claim depends on what it records and how
it is deployed; measurement and optimisation choices have to be designed for
the deployment from the start, rather than added afterwards. The system and
the evaluation tooling built here provide a base for doing both.

\section{Limitations}
\label{concl:sec:limitations}

\paragraph{Chat history is not stored.} The deployed system does not save
chat conversations on the server; a student's chat history exists only in
their browser for the duration of the session. The database stores quiz
answers and the feedback notes written after each quiz, but not chat
questions or answers. As a result, the analytics are built on quiz and
assignment results rather than on the questions students ask in chat, and the instructor-hours measure of
\autoref{eval:subsec:hours}, which counts deflected chat queries, cannot yet
be computed from the system's own records.

\paragraph{The adaptive quiz's rule table is not validated.} The table that
maps a student's performance tier to a target Bloom's level and complexity
(\autoref{impl:sec:analytics}) follows established principles but was set by
design rather than calibrated against instructors' judgement or student
outcomes. Whether its targets are the right ones for a given course is
untested.

\paragraph{Storing chat histories for analytics.}
Storing each user's chat history on the server --- with NUS IRB approval
and the pseudonymisation scheme of \autoref{design:sec:methodology} --- would close the limitation above. It would allow the
instructor-hours measure to be computed directly from deflected queries, and
would let the instructor analytics draw on the questions students actually
ask, for example by clustering them by topic, alongside quiz and assignment results.

\paragraph{Fitting compression to the deployment.} The answer-quality
evaluation (\autoref{eval:sec:results:quality}) points to four concrete
changes. The compressor should keep code rather than strip it, since course
material such as IT5001's states key facts in code, and stripping it
produced garbled quotations. Its embedding step should run where retrieval's
embeddings already are, or on a hosted embedding service, so that it costs
milliseconds rather than seconds. The retrieval distance cut-off should be
calibrated per course, since off-syllabus and in-syllabus distances
overlapped. And the persona should tell the student when the course material
does not cover a question even when no excerpts are provided, which no answer
did in either condition.

\paragraph{Adaptive, evidentiality-guided compression.} A fixed threshold
and cap are suboptimal per question, as the dropped equation in
\autoref{eval:sec:results:compression} showed; evidentiality-guided
compression with an adaptive ratio, as in ECoRAG~\cite{facl25:Jeong}, is the
natural upgrade, at the cost of an LLM-in-the-loop labelling pipeline.

\paragraph{Validating the adaptive quiz.} The quiz's rule table could be
validated by asking instructors to rate whether its target Bloom's level and
complexity suit students at each performance tier, and by checking whether
students who follow its targets improve faster than those given questions at
random levels.

\paragraph{Trimming the fixed prompt overhead.} The token audit
(\autoref{design:subsec:tokenaudit}) found that tool definitions and the
system prompt make up about three-quarters of each agent pass's prompt,
re-sent on every pass. Sending only the tools a turn is likely to need ---
for example, omitting the documentation tools for questions about course
logistics --- and shortening the tool descriptions would cut input tokens on
every pass, alongside what compression saves on retrieved context.

\paragraph{Broader evaluation of the compression stage.} The compression
results come from small samples on two small corpora; a larger, multi-rater
question set across several courses is needed
(\autoref{eval:sec:discussion}).

\paragraph{Production-hardened deployment.} The prototype runs on a single
application host (\autoref{design:sec:architecture}). A production target on
AWS has been designed but not provisioned: a managed PostgreSQL database with
pgvector, the backend on container orchestration behind a load balancer
(rather than serverless functions, which time out on streamed, multi-pass
chat), a GPU group in place of the local inference host, managed identity,
scheduled ingestion, and the usual network hardening. Building and costing
this target --- and the equivalent deployments on GCP and Azure, along the
dimensions of \autoref{impl:tab:providers}, which would also test the choice
of AWS --- would show whether the per-student cost of
\autoref{eval:subsec:results:cost} holds at institutional scale.
