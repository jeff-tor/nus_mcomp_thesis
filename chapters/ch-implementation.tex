\chapter{Implementation}
\label{ch:implementation}
\vspace{2em}

This chapter describes how the design of \autoref{ch:design} was built.
\autoref{impl:sec:stack} covers the technology stack and the configurations
the system ran in. \autoref{impl:sec:retrieval} describes the knowledge base,
\autoref{impl:sec:qa} the chat agent, its prompts, and the model provider

\autoref{impl:sec:analytics} describes the instructor-facing analytics and the
adaptive quiz that feeds them.

\section{Technology Stack}
\label{impl:sec:stack}

The system is deliberately light on dependencies, in keeping with NFR7. The
backend is a single Node.js~20 service written without a web framework; its
only runtime dependencies are the PostgreSQL client and the Model Context
Protocol (MCP) SDK. The browser client is plain HTML, CSS, and JavaScript
modules, with no framework or build step. The adaptive quiz's fuzzy-inference
engine is a small Python program that the backend runs per call
(\autoref{impl:sec:analytics}). Data lives in PostgreSQL~16 with the pgvector
extension, which serves as both the relational store and the vector index.
Models are served by Ollama (embeddings and local generation) and Groq
(hosted generation); web search uses the Tavily API. The backend, the
database, and Nginx run as Docker containers on one EC2 host, built and
deployed through continuous integration.

\autoref{impl:fig:components} in \autoref{append:comparisons} shows how the
application is organised, and \autoref{append:architecture} gives the full
master architecture diagram with the path of each use case. The
browser client is a set of plain JavaScript modules, one per feature, over a
single shared state. Every request passes through Nginx and an
authentication gate that checks the session cookie and the user's role, so
instructor-only routes are refused on the server rather than merely hidden
in the interface. Each feature then has one request handler, and the
handlers share a set of services: retrieval, embeddings, the agent's tools,
an MCP client for external documentation servers, the LLM provider router,
a single database-access module, a fuzzy-inference feedback engine
(in Python) for the adaptive quiz, and web search. Each service is loaded
independently, so one that fails to load disables only the feature that
depends on it.

\subsection{Cloud Provider Selection}
\label{impl:subsec:provider}

The hybrid deployment chosen in \autoref{design:subsec:deployment-decision}
needs a cloud platform for the application server and database.

\autoref{impl:tab:providers} in \autoref{append:comparisons} compares the
three major cloud providers across ten dimensions that drive this system's
implementation, from managed AI services to pricing and learning curve.

The application server runs on AWS EC2 (us-east-1). AWS was chosen as the
industry-standard platform for deploying cloud-based components; a systematic
comparison of service level and cost against GCP and Azure, along the
dimensions of \autoref{impl:tab:providers}, is left to future work
(\autoref{ch:concl}).
Generation, however, is not served by any of the three platforms' managed AI
services but by a dedicated inference provider, selected separately
(\autoref{impl:subsec:llm-providers}).

\section{Knowledge Base and Retrieval}
\label{impl:sec:retrieval}

Course materials are ingested offline, never on the request path
(\autoref{impl:fig:ingest}). Files are organised in one folder per course
code, split into chunks of about 900 characters with 150 characters of
overlap, embedded with BGE-M3, and stored in pgvector under an HNSW index.
Re-ingesting a document replaces its chunks rather than duplicating them.
Because the ingestion job uses the same embedding module and the same
database module as the live application, the vectors it writes are exactly
those that retrieval reads. At query time, the question is embedded with the
same model, the five nearest chunks for the student's current course are
retrieved, and any whose cosine distance exceeds 0.6 are discarded. If none
remain, or if retrieval fails, the turn proceeds without course material
rather than failing.

Administrative data --- courses, assignments, deadlines, and grades --- is
not ingested but fetched live from the learning management system. Two
providers are supported. For Canvas, each user links their own account
through OAuth~2.0, and the server stores and refreshes their token; where an
institution issues no developer key, as at NUS, a shared personal access
token is used instead. For Google Classroom, an OAuth refresh token is held
server-side. Both providers' responses are normalised to one shape, so the
dashboards, calendar, and chat agent read the same structure whichever
provider is connected.

\section{Question Answering and Personalisation}
\label{impl:sec:qa}

\autoref{impl:fig:chatturn} traces one chat turn. The student's identity is
taken from the server-side session, never from the browser. The question is
embedded and the five closest course excerpts are retrieved, optionally
passing through the compression stage of \autoref{impl:sec:compression}. A
persona prompt then frames the excerpts: the assistant is Socratic, bound by
academic-integrity rules, and told to cite the excerpts it uses. The agent
loop runs for up to five passes, calling tools --- a practice-question
generator, a lookup of the student's progress, a search over other courses,
and external documentation servers via MCP --- and feeding their results
back before answering. The answer streams to the browser token by token
over server-sent events.

The persona prompt is defined on the server, so the browser cannot replace
it; any system message the client sends is discarded. It casts the assistant
as a patient teaching assistant that teaches Socratically --- a hint or
guiding question before a full solution --- and never writes graded work on
the student's behalf, while encouraging fully worked practice examples
(NFR5). It instructs the model to treat retrieved excerpts as its primary
source, to say which excerpt it used, and to say so when the excerpts do not
cover the question rather than guess (FR1). Personalisation enters through
the context the persona wraps: the student's courses, deadlines, and grades,
and, through the progress tool, their per-course quiz performance. The full
prompts are reproduced in \autoref{append:prompts}.

The turn is designed so that no single failure fails the request. If
retrieval fails, the turn continues with the persona alone; a tool that
fails returns an error that the model explains; a missing search key simply
disables search.

\subsection{LLM Provider Layer and Local Fallback}
\label{impl:subsec:llm-providers}

All text generation goes through a single provider layer that selects a
provider and model \emph{per role}: the \emph{chat} role covers student chat,
the tool-calling agent loop, and generated notes; the \emph{quiz} role covers
question generation and end-of-quiz feedback. Each provider implements the
same four operations --- streaming chat with tool calls, one-shot JSON
completion, model listing, and configuration --- so the call sites (chat,
quiz, recommendations, analytics) do not depend on which provider serves
them. Two providers are implemented: Ollama for local models (which also
serves embeddings), and Groq through its OpenAI-compatible chat-completions
endpoint. A third, Gemini, was removed after the vendor retired the model the
system used.

The Groq provider bridges two protocol differences. Tool-call arguments are
an object in the system's internal format but a JSON string on the
OpenAI-compatible wire format. Tool replies must carry the identifier of the
call they answer, whereas Ollama matches replies by position; the provider
therefore assigns identifiers from the preceding assistant turn in call
order.

Hosted validation also exposed a latent bug. Groq checks tool-call arguments
against the declared JSON schema; gpt-oss-120b sent \texttt{null} for an
optional parameter, and every multi-part turn was rejected (10/10). Ollama
had silently accepted the same calls. Declaring optional parameters as
nullable removed the errors (0/10) and was verified in production.

A fallback wrapper retries a failed hosted call on the local model, under
three rules: it never switches a stream that has already emitted tokens,
which would splice two different answers together; it never retries after
the caller's own deadline; and after an availability failure (rate limiting,
a server error, or a network error) it skips the hosted provider for a
cooldown period. The fallback model is Llama~3.2 (3B) rather than the more
capable Qwen3 14B, because only the smaller model stays resident in memory
beside the embedding model; a cold load of the fallback (27.7\,s under
memory pressure) would exceed the quiz latency budget by an order of
magnitude, so the fallback model is kept permanently loaded. With the hosted
provider forced unreachable in production, quiz generation fell back in
1.28\,s and an agent pass in 0.81\,s.

The deployed configuration assigns gpt-oss-20b to the chat role and
gpt-oss-120b to the quiz role, both at low reasoning effort with a
1\,024-token completion cap; the evidence for this split is reported in
\autoref{eval:sec:results:providers}. Keeping the two roles on different
models also gives each its own rate-limit budget on the provider.

\section{Context Compression for Token Reduction}
\label{impl:sec:compression}

When the compression stage was developed and evaluated, response generation
ran on a small, locally hosted language model (Llama~3.2, 3B parameters, served
through Ollama on an 8\,GB consumer laptop; \autoref{impl:tab:configs}). Under standard retrieval-augmented generation
(RAG)~\cite{neurips20:Lewis}, the top-$N$ retrieved chunks of course material are
prepended to the prompt in full, even though each chunk is typically only
partially relevant to the student's question. This inflates prompt length --- the
dominant cost for a compute-bound local model --- and risks distracting the model
with irrelevant context, a failure mode documented for long-context
inputs~\cite{tacl24:Liu}.

To address this, the pipeline implements a lightweight context-compression stage
inspired by \textsc{Recomp}~\cite{iclr24:Xu}, which proposes compressing retrieved
passages before generation and, crucially, \emph{selective augmentation}:
returning an empty context when nothing relevant survives compression, rather than
forcing the model to attend to noise. The implementation here is the untrained
extractive variant: instead of the paper's fine-tuned contrastive compressor, it
selects existing sentences by embedding similarity, making it faithful by
construction (the compressor cannot introduce content that was not retrieved).

The stage is inserted between the existing retriever and the generation call
(\autoref{impl:fig:chatturn}, lower row), and proceeds as follows:

\begin{enumerate}[nosep]
  \item retrieved chunks are segmented into candidate sentences, with markdown
        structure and code fences stripped;
  \item each candidate sentence is embedded with the system's existing retrieval
        embedder (BGE-M3~\cite{arxiv24:Chen}) in a single batched call;
  \item each sentence is scored by cosine similarity against the query embedding,
        which is reused from the retrieval step at no additional cost;
  \item sentences scoring above a threshold $\tau$ are retained, highest first,
        capped at $k$ sentences; if none qualifies, the context is left empty
        (selective augmentation) and the model is instructed to state that the
        topic is not covered by the course materials.
\end{enumerate}

Reusing the retrieval embedder is a deliberate engineering choice: the compressor
adds no new model, dependency, or runtime to the stack (about 100 lines of
JavaScript), which matters on the memory-constrained host described in
\autoref{impl:sec:stack}. The stage is deployed behind a runtime feature flag
(\texttt{RAG\_COMPRESS}, with $\tau$ and $k$ configurable), which both protects
the production path and enables the controlled A/B comparison reported in
\autoref{eval:sec:results}.

The stage remains relevant under the later hybrid configuration, for a
different reason. With hosted generation, retrieved context is billed per
token rather than paid for in prefill latency, and in the tool-calling agent
loop it is re-sent on every pass, so the tokens compression removes are
saved several times per turn (\autoref{eval:subsec:results:cost}).

\section{Analytics and Feedback Loop}
\label{impl:sec:analytics}

The analytics are built on two sources: quiz results, which the system
stores, and assignment results, which it fetches from the learning management
system. They do not use the questions students ask in chat, which are not
stored (\autoref{concl:sec:limitations}). The quiz is also the system's main
personalisation mechanism (FR5), so it is described first.

\paragraph{Adaptive quiz.} Each student has a running performance score per
course: an exponential moving average of their answers ($\alpha = 0.2$, with
a correct answer scored 10 and a wrong one 0). A fuzzy-inference engine maps
this score to the next question's target. Seven overlapping trapezoidal
fuzzy sets~\cite{ic65:Zadeh}, from \emph{novice} to \emph{expert}, cover the
score range; each tier maps to a range of Bloom's taxonomy levels and a
complexity band from 1 to 5, and the outputs are the membership-weighted
averages of the tiers' targets, as in a zero-order Takagi--Sugeno
system~\cite{smc85:Takagi}. The overlap means a score near a tier boundary
moves the target gradually rather than in a step.

The rule table that maps tiers to targets is a design heuristic, built on two
principles from the learning-sciences literature. First, the revised Bloom's
taxonomy orders cognitive processes from remembering, through understanding,
applying, analysing, and evaluating, to creating, each building on those
below it~\cite{book01:Anderson}; a student who has not yet shown reliable
recall is therefore not given analysis or evaluation questions. Second, the
target sits just beyond what the student currently demonstrates, in the
spirit of the zone of proximal development~\cite{book78:Vygotsky}: above the
lowest tier, each tier spans two adjacent Bloom's levels, the lower one
consolidating and the upper one stretching. Complexity rises with the tier
for the same reason, and the top tier keeps the highest two levels but raises
complexity, since there is no level above creating. The table has not been
validated with instructors (\autoref{concl:sec:limitations}).
The question itself is taken from the question bank when one matches the
target; otherwise the quiz model generates one, grounded in a random excerpt
of the course's ingested notes, and caches it in the bank. When a sitting
ends, the model writes one short feedback note for the attempt --- what the
student did well, what to improve, and one next step --- grounded only in
the questions of that attempt. Every answer and every note is stored.

\paragraph{Student analytics.} From the stored attempts, each student sees
their accuracy per Bloom's level, the trajectory of their running score, the
questions they first missed and later recovered, and the themes that recur
across their feedback notes. Alongside these, the dashboards and course
overview show the student's assignment grades and deadlines from the
learning management system.

\paragraph{Instructor analytics.} Instructors, and only instructors (the role
is checked on the server, NFR3), see every student's per-course performance
profile. For a chosen course they can also request a course-improvement
note. The server recomputes the class signals from the database --- overall
accuracy, the number of students below 50\%, the questions with the lowest
class accuracy, and the themes recurring in the feedback notes written for
the class --- so the figures cannot be altered by the browser. It combines
them with live web-search results on the subject and the course's
assignment titles and due dates from the learning management system, and asks the note model for concise recommendations:
where students struggle, whether the coursework covers it, what emerging
topics to add, and one concrete change for the next run. The prompt forbids
inventing statistics, assignments, or student names; when there is no quiz
activity or no coursework, it tells the model so explicitly, after testing
showed that the model otherwise invented both. The note streams back in the
same format as chat.

\paragraph{What is not yet captured.} Chat turns are not yet stored on the
server: the conversation history lives only in the browser. Requirement FR3
is therefore met for quiz interactions but not yet for chat, and analytics
over the questions students ask in chat --- including the topic clustering
proposed in \autoref{eval:subsec:hours} --- depend on adding that logging
(\autoref{concl:sec:limitations}).

\section{Summary}
\label{impl:sec:summary}

The system is a single, lightly dependent Node.js service with a
PostgreSQL and pgvector store, deployed in containers on one EC2 host. Course
materials are ingested offline and retrieved per question; administrative
data is fetched live from Canvas or Google Classroom. A server-defined
persona and a tool-calling agent loop answer students, generating text
through a provider layer that routes to hosted models and falls back to a
local one. An optional compression stage trims retrieved context before
generation. An adaptive quiz personalises practice through fuzzy inference,
and its stored attempts feed both student and instructor analytics. The main
gap is that chat turns are not yet logged on the server, which the
instructor-hours evaluation requires. \autoref{ch:evaluation} evaluates the
compression stage and the deployment model, and defines the instructor-hours
measure.
