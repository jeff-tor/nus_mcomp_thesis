\subsection{Local versus Hosted Inference Benchmark}
\label{eval:subsec:setup:providers}

To choose a deployment model (\autoref{design:subsec:deployment-decision}),
local and hosted inference were compared on the same prompts, tools, and
tasks. The local runs used a MacBook Pro M1 Max (32\,GB) running Ollama with
4-bit quantised models (Llama~3.2 3B, Qwen3 8B, Qwen3 14B; thinking
disabled). The hosted runs used Groq's on-demand free tier (gpt-oss-20b,
gpt-oss-120b, Qwen3.8 27B) at low reasoning effort with a 1\,024-token
completion cap. Local agent runs were made in August 2026; hosted runs and
the local quiz run on 27 September 2026.

\paragraph{Agent benchmark.} A harness replicates the production agent loop
--- the same tool definitions and persona, a five-iteration cap, and tools
withheld on the final pass --- with tool results stubbed so that every model
receives byte-identical inputs. Four scenarios were run: a concept
explanation with no tool expected, a single tool lookup, a course-material
retrieval ($n=3$ each), and the headline multi-part turn --- a progress
lookup followed by a practice question ($n=10$). A turn is scored
\emph{grounded} if the answer states the student's stubbed score and names a
stubbed weak topic. The same rubric was applied to both regimes, and
re-scoring the earlier local runs reproduced their original hand-coded
grounding results exactly. Hosted latency is the sum of HTTP request times
per turn, excluding rate-limit pauses.

\paragraph{Quiz benchmark.} The production multiple-choice prompt was run
unchanged over five rotating topics ($n=10$ per model, temperature 0.7),
with the same parse and schema check as production. Answer-key correctness
was then judged by a single, unblinded rater.

\subsection{Instructor-Hours Returned}
\label{eval:subsec:hours}

The headline workload metric promised in \autoref{review:subsec:gap} is
defined as follows. A student query is counted as \emph{deflected} when the
assistant answers it from the course corpus without instructor involvement
--- routine clarification, content-navigation, and logistics questions that
would otherwise reach the teaching staff. The estimated instructor-hours
returned per course per week is then

\begin{equation}
  \label{eval:eq:hours}
  H_{\mathrm{returned}}
    \;=\;
  \frac{1}{W} \sum_{q \,\in\, Q_{\mathrm{deflected}}} t_{\mathrm{handle}}(q),
\end{equation}

where $Q_{\mathrm{deflected}}$ is the set of deflected queries logged over an
observation window of $W$ weeks and $t_{\mathrm{handle}}(q)$ is the time an
instructor or teaching assistant would have spent answering query $q$
manually. Routine queries are assigned a deliberately conservative handling
time of 2--5 minutes, so $H_{\mathrm{returned}}$ is reported as a range whose
lower bound understates the true relief (it excludes context-switching costs
and out-of-hours response burden). Because every interaction is logged by the
deployed system, the metric reduces to a single aggregation over the
assistant's query logs.

\subsection{Token, Cost, Latency, and Answer-Quality Metrics}
\label{eval:subsec:tokenmetrics}

The compression stage is evaluated on the comparison dimensions the
prompt-compression literature itself uses
(\autoref{review:subsec:compression}), so that the evaluation speaks the same
metric language as the problem statement
(\autoref{intro:sec:problem}) and the baseline token audit
(\autoref{design:subsec:tokenaudit}):

\begin{enumerate}[nosep]
  \item \textbf{Input tokens per query}, before versus after compression,
        reported with the compression ratio --- the direct measure of the
        token inflation identified in \autoref{review:subsec:tokens};
  \item \textbf{Cost per query and per student per semester}, computed from
        the hosted provider's per-token list prices; for locally hosted
        generation, where no per-token charge exists, latency and
        memory-residency effects are reported instead;
  \item \textbf{End-to-end latency} (retrieval $\rightarrow$ compression
        $\rightarrow$ generation), including the compression stage's own
        overhead --- compression adds an inference step, and its cost is
        reported rather than netted out, following the practice
        of~\citet{facl25:Jeong}~\cite{facl25:Jeong};
  \item \textbf{Answer quality} on course-material question answering, to
        verify that compression does not degrade answers --- mirroring how
        \textsc{Recomp} and TCRA-LLM report the compression--quality
        trade-off~\cite{iclr24:Xu, femnlp23:Liu}.
\end{enumerate}

The per-student-per-semester projection under dimension 2 --- baseline versus
compressed, extrapolated to a realistic course enrolment and set beside the
US\$7.50 per student per course per semester observed for
Ethel~\cite{tpt24:Kortemeyer} --- connects the evaluation directly back to
the institutional cost evidence of \autoref{intro:sec:problem}.

\subsection{Context Compression: Token Reduction and Latency}
\label{eval:sec:results:compression}

The compression stage of \autoref{impl:sec:compression} was evaluated end-to-end
against the uncompressed RAG baseline on the deployed stack: identical questions,
identical retrieved chunks, generation by Llama~3.2 at temperature~0, with prompt
and output token counts taken directly from the inference runtime
(\texttt{prompt\_eval\_count}). The probe used the ingested CS3241 (computer
graphics) corpus with two in-syllabus questions --- Q1 on shadow rays, Q2 on
ray--sphere intersection --- and one deliberately out-of-syllabus question (Q3, on
TCP congestion control), with compression parameters $\tau = 0.5$, $k = 6$.
\autoref{eval:tab:compression} summarises the results.

\begin{table}[htb]
  \centering
  \caption{Uncompressed RAG versus extractive compression ($\tau=0.5$, $k=6$) on
           the deployed system. Compressed latency includes the compression
           overhead itself (1.1--2.0\,s per query on the 8\,GB host).}
  \label{eval:tab:compression}
  \begin{tabular}{l r r r}
    \hline
    \textbf{Metric} & \textbf{Raw RAG} & \textbf{Compressed} & \textbf{Change} \\
    \hline
    Prompt tokens, Q1            & 769            & 257           & $-66.6\%$ \\
    Prompt tokens, Q2            & 545            & 195           & $-64.2\%$ \\
    Response tokens, Q1          & 354            & 122           & $-65.5\%$ \\
    Response tokens, Q2          & 91             & 86            & $-5.5\%$  \\
    End-to-end latency, Q1       & 17.2\,s        & 7.7\,s        & $-55\%$   \\
    End-to-end latency, Q2       & 5.7\,s         & 5.2\,s        & $-9\%$    \\
    Context retained (chars), Q1 & 100\%          & 26.9\%        & ---       \\
    Context retained (chars), Q2 & 100\%          & 18.7\%        & ---       \\
    Off-syllabus context, Q3     & $\sim$446 tok. & 0 (empty)     & ---       \\
    \hline
  \end{tabular}
\end{table}

Three observations follow. First, compression removed roughly two-thirds of the
prompt tokens on in-syllabus questions while retaining the sentences that answer
them (the top-scoring sentence for Q1 was the corpus sentence defining shadow
rays, at cosine similarity 0.66). Because a compute-bound local model's latency
scales with prompt length, this translated into a net end-to-end speed-up
despite the added compression step. Second, the shorter, more focused context
also changed generation behaviour: on Q1 the baseline produced a longer answer
that drifted into adjacent material, whereas the compressed run stayed on the
retrieved definition, consistent with the distraction effect reported
by~\citet{tacl24:Liu}~\cite{tacl24:Liu}. Third, selective augmentation behaved as
designed: for the out-of-syllabus Q3, every candidate sentence scored below
$\tau$ (0.40--0.42, against 0.57--0.82 for in-syllabus sentences), so no context
was injected and the model correctly reported the topic as outside the course
materials; at a looser $\tau = 0.4$ the same query leaked three marginal
sentences, illustrating that $\tau$ is the precision--recall control of the
stage.

Compression is not uniformly beneficial, however. On Q2 the sentence containing
the ray--sphere intersection \emph{equation} itself scored below the retention
cut-off, and the compressed answer, while correct about the discriminant, could
no longer reproduce the equation --- an answer-quality regression directly
attributable to over-compression. This mirrors the recall risk inherent to
extractive compression~\cite{iclr24:Xu} and motivates the conservative default
($\tau = 0.5$ with $k = 6$) and the per-deployment tunability noted in
\autoref{impl:sec:compression}. These results are indicative rather than
statistically robust: they derive from a three-question probe over a single
course corpus, and a larger question set across multiple courses is required
before the reductions can be claimed as general.

\label{eval:sec:results:providers}

The two gpt-oss models were 1.5--6.6 times faster end to end than the local
models usable for production (Llama~3.2 and Qwen3 14B) and matched the best
of them on grounding (10/10). The only faster local model, Qwen3 8B, never
called the expected tools and grounded only 3/10 turns. Generation throughput differed by 6--50 times: about
19--75 tokens per second locally against 475--965 hosted. These hosted
latencies are conservative for production: the same calls made from the
application server on EC2 took 229--256\,ms per agent pass, two to five
times faster than from the benchmark client. In the local regime, by
contrast, latency in production was dominated not by generation but by cold
model loads and by embedding over the SSH tunnel (1.2--1.7\,s, against
0.12\,s on the host itself).

Two further observations matter for the token argument of this thesis.
First, the hosted gpt-oss models took three passes per multi-part turn where
the local models took two, chaining the two tools sequentially; each pass
re-sends the full prompt, which is why their input-token counts are higher.
Second, the gpt-oss models always reason, and reasoning is billed as output:
at medium reasoning effort a quiz question consumed 400--650 reasoning tokens
against 10--50 at low effort, for equally valid output --- a hidden
output-token multiplier with no visible benefit, which is why the deployment
uses low effort.

Parse validity overstated quality for every model: questions that passed
the production schema check still had wrong answer keys, duplicate options,
or two correct options. Reported quiz quality therefore needs an
answer-correctness check, not only schema validity. These results set the
deployed role split: gpt-oss-20b for the agent (1.3 times faster than
gpt-oss-120b, half the cost per turn, equally grounded, and unaffected by the
nullable-argument bug), and gpt-oss-120b for quizzes (8/10 correct keys
against 6/10, for US\$0.00007 more per question).

\subsection{Cost per Query and per Student}
\label{eval:subsec:results:cost}

The benchmark prompts carry no retrieved context, so production cost is
modelled by adding about 1\,000 tokens of retrieved context per pass, with
and without the 65\% reduction measured in the compression probe
(\autoref{eval:sec:results:compression}). Costs use Groq's list prices
(gpt-oss-20b: US\$0.075 input and US\$0.30 output per million tokens;
gpt-oss-120b: US\$0.15 and US\$0.60; retrieved 27 September 2026). The
per-semester projection assumes 20 chat turns, 10 quiz questions, and one
quiz-feedback note per student per week over 13 weeks. These are
round-number assumptions, not measured usage.

\begin{table}[htb]
  \centering
  \caption{Projected generation cost per student per semester (US\$).}
  \label{eval:tab:cost}
  \footnotesize
  \begin{tabular}{l r r r}
    \hline
    \textbf{Model split} & \textbf{No retrieval} & \textbf{+ RAG}
      & \textbf{+ RAG + compression} \\
    \hline
    Agent 20b, quiz 120b (deployed) & 0.090 & 0.148 & 0.110 \\
    Agent 120b, quiz 20b            & 0.141 & 0.258 & 0.182 \\
    All 120b                        & 0.152 & 0.269 & 0.193 \\
    \hline
  \end{tabular}
\end{table}

With retrieved context included, projected cost is US\$0.11--0.27 per
student per semester, against the US\$7.50 per student per course per
semester reported for Ethel~\cite{tpt24:Kortemeyer}. The comparison is
indicative only: Ethel used a different model class, different usage
patterns, and 2024 pricing, and a single institution's figure should not be
read as a general benchmark.

The agent loop adds a mechanism the literature reviewed in
\autoref{review:subsec:tokens} does not isolate: \emph{tool use multiplies the
prompt}. Each pass re-sends the system prompt, the retrieved context, and the
tool schemas, so context injected once per turn is billed once per pass ---
three times on the multi-part turn. Compressing a 1\,000-token context by
65\% therefore cuts the cost of a gpt-oss-20b agent turn by about 30\%
(US\$0.00049 to US\$0.00034), more than the same compression saves in
single-pass RAG. Token counts are not comparable across model families ---
the same prompt counted 1\,093 tokens under Llama~3.2, 758 under Qwen3, and
672 under gpt-oss --- so compression ratios are compared within a model only.

Rate limits are a separate capacity constraint. The free tier allows 8\,000
tokens per minute per model; at about 5\,500 tokens per retrieval-augmented
agent turn, one model serves roughly 1.4 turns per minute across all users,
so a production deployment at course scale requires a paid tier.

\section{Discussion}
\label{eval:sec:discussion}

% TODO: Interpret the results against the problem statement and threats to
% validity.
\draftnote{overall discussion against the problem statement.}

Both inference regimes reward fewer input tokens, for different reasons. In
the hosted regime, tokens are billed directly and multiplied by agent passes;
in the local regime, they appear as prefill latency and, more acutely, as
memory pressure on a host shared with the retriever. This supports the claim
in \autoref{intro:sec:problem} that input tokens per query are the primary
controllable cost driver in both regimes.

\paragraph{Threats to validity of the provider benchmark.}
Samples are small ($n=10$ for the headline scenario and quizzes, $n=3$
otherwise): enough to rank models, not to support P95 latencies or
fine-grained claims. The local and hosted agent runs were five weeks apart, on
different Ollama versions, although prompts, stubs, and loop were identical.
Hosted latencies include trans-Pacific round trips from the benchmark client.
Quiz correctness was judged by a single, unblinded rater over five computer
science topics. Stubbed tool results measure model behaviour rather than
live-data effects, and no complete production turn (retrieval, live tools,
and streaming) was timed on the hosted provider. Free-tier throttling was
excluded from latency, and queueing on paid tiers may differ. Finally, the
cost projection rests on assumed usage rates.
