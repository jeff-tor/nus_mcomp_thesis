\chapter{Evaluation and Results}
\label{ch:evaluation}
\vspace{2em}

This chapter evaluates the system against the three research questions of
\autoref{design:sec:methodology}: how the instructor time the assistant
returns can be measured in hours (RQ1), what retrieval compression saves and at what cost to answer
quality (RQ2), and which deployment model best meets the cost, latency, and
quality requirements (RQ3). \autoref{eval:sec:setup} describes the
experimental setup, \autoref{eval:sec:metrics} defines the metrics, and
\autoref{eval:sec:results} reports the results, which
\autoref{eval:sec:discussion} interprets. RQ2 and RQ3 are answered by
measurement. RQ1 is answered by the measure defined in
\autoref{eval:subsec:hours} and the data it requires; applying it to the
deployed system is left to future work, because chat turns are not yet
stored (\autoref{concl:sec:limitations}).

\section{Experimental Setup}
\label{eval:sec:setup}

\subsection{Answer-Quality Evaluation}
\label{eval:subsec:setup:quality}

To measure what compression costs in answer quality (RQ2), 24 questions were
written over the IT5001 (Python programming) corpus, a larger course than the
CS3241 corpus of the compression probe: six lecture notes of about 2\,700
words. Twenty questions are in-syllabus, spread across all six lectures, each
with a reference answer taken from the notes; five of these are tagged
\emph{code}, because their key fact appears only in code, which the
compressor strips (\autoref{impl:sec:compression}), and fifteen
\emph{prose}. Four are off-syllabus, one of them a topic from another course
(CS5000), to test whether the assistant says when the material does not cover
a question.

Each question was answered twice on the deployed system on 19 October 2026,
with retrieval exactly as in production (the five nearest chunks, cosine
distance at most 0.6): once with every retrieved chunk in full
(\emph{uncompressed}) and once with \textsc{Recomp}-lite compression ($k = 6$,
$\tau = 0.5$; \emph{compressed}). Both answers used the production persona,
gpt-oss-20b at temperature~0, and no tools, so the retrieved context was the
only difference between them. The two answers to each question were labelled
A and B in a seeded random order, so that scoring was blind to the condition.

Each in-syllabus answer was scored against its reference: 2 if correct and
complete, 1 if partly correct (missing a key point, or with a minor error),
and 0 if wrong or if it conveyed none of the reference. The persona instructs
the assistant to teach Socratically, so some answers ask guiding questions
instead of answering; these were scored 1 if the hint stated at least one key
fact of the reference and 0 if it only asked questions, and were recorded as
\emph{Socratic}. Each answer was also marked for whether it drew on the course
material, and each off-syllabus answer for whether it said the material did
not cover the question.
An AI assistant (Claude Opus 5.5) suggested a provisional score for every
answer, with a one-line justification, before the A/B key was opened; the
author then read each answer against its reference and reviewed every
provisional score, changing none of the 96.

\subsection{Local versus Hosted Inference Benchmark}
\label{eval:subsec:setup:providers}

To choose a deployment model (\autoref{design:subsec:deployment-decision}),
local and hosted inference were compared on the same prompts, tools, and
tasks. The local runs used a MacBook Pro M1 Max (32\,GB) running Ollama with
4-bit quantised models (Llama~3.2 3B, Qwen3 8B, Qwen3 14B; thinking
disabled). The hosted runs used Groq's on-demand free tier (gpt-oss-20b,
gpt-oss-120b, Qwen3.8 27B) at low reasoning effort with a 1\,024-token
completion cap. Local agent runs were made in August 2026; hosted runs and
the local quiz run on 27 September 2026.

\paragraph{Agent benchmark.} A harness replicates the production agent loop
--- the same tool definitions and persona, a five-iteration cap, and tools
withheld on the final pass --- with tool results stubbed so that every model
receives byte-identical inputs. Four scenarios were run: a concept
explanation with no tool expected, a single tool lookup, a course-material
retrieval ($n=3$ each), and the headline multi-part turn --- a progress
lookup followed by a practice question ($n=10$). A turn is scored
\emph{grounded} if the answer states the student's stubbed score and names a
stubbed weak topic. The same rubric was applied to both regimes, and
re-scoring the earlier local runs reproduced their original hand-coded
grounding results exactly. Hosted latency is the sum of HTTP request times
per turn, excluding rate-limit pauses.

\paragraph{Quiz benchmark.} The production multiple-choice prompt was run
unchanged over five rotating topics ($n=10$ per model, temperature 0.7),
with the same parse and schema check as production. Answer-key correctness
was then judged by an AI model rather than a human rater: a single,
unblinded LLM-based review of each question against its keyed answer. The
correct-key rates are therefore indicative only, and a human-rated,
course-specific item set is required before they can be relied on.

\section{Evaluation Metrics}
\label{eval:sec:metrics}

Each research question has its own metrics. RQ1 is measured in
instructor-hours returned per course per week
(\autoref{eval:subsec:hours}). RQ2 and RQ3 share a set of per-query metrics
--- input tokens, cost, end-to-end latency, and answer quality
(\autoref{eval:subsec:tokenmetrics}) --- and RQ3 adds grounding fidelity and
quiz answer-key correctness, defined with the benchmark in
\autoref{eval:subsec:setup:providers}.

\subsection{Instructor-Hours Returned}
\label{eval:subsec:hours}

The headline workload metric promised in \autoref{review:subsec:gap} is
defined as follows. A student query is counted as \emph{deflected} when the
assistant answers it from the course corpus without instructor involvement
--- routine clarification, content-navigation, and logistics questions that
would otherwise reach the teaching staff. The estimated instructor-hours
returned per course per week is then

\begin{equation}
  \label{eval:eq:hours}
  H_{\mathrm{returned}}
    \;=\;
  \frac{1}{W} \sum_{q \,\in\, Q_{\mathrm{deflected}}} t_{\mathrm{handle}}(q),
\end{equation}

where $Q_{\mathrm{deflected}}$ is the set of deflected queries logged over an
observation window of $W$ weeks and $t_{\mathrm{handle}}(q)$ is the time an
instructor or teaching assistant would have spent answering query $q$
manually. Routine queries are assigned a deliberately conservative handling
time of 2--5 minutes, so $H_{\mathrm{returned}}$ is reported as a range whose
lower bound understates the true relief (it excludes context-switching costs
and out-of-hours response burden). Once every chat turn is logged on the server,
the metric reduces to a single aggregation over the assistant's query logs;
at present only quiz interactions are stored (\autoref{impl:sec:analytics}).

This definition answers RQ1. Computing it requires the system to record,
for every chat query, the course it concerns, when it was asked, and its
text, so that it can be classified as routine and counted as deflected.
The deployed system records quiz interactions but not chat turns
(\autoref{impl:sec:analytics}), so no measured instructor-hours are reported
in this thesis; storing chat histories, which would make the measure
computable, is future work (\autoref{concl:sec:limitations}).

\paragraph{Illustrative projection.} To indicate the likely scale, the measure
can be projected from stated assumptions rather than logs
(\autoref{append:tab:hours}). Weekly hours returned are the product of
enrolment (200--300), questions per student per week (0.14--0.59, from the
KAIST deployment's conversations and exchanges over 14
weeks~\cite{acl25:Kweon}), the share that are routine, the share answered
fully correctly (65\%, \autoref{eval:sec:results:quality}), the share that
would otherwise have reached staff, and the handling time per question. The
handling time is modelled as reading the question (238 words per
minute~\cite{jml19:Brysbaert}), looking up the answer, and composing a reply
(19 words per minute when composing~\cite{chi99:Karat}), giving 2.7--8.4
minutes. The projection ranges from 0.1 to 7.2 instructor-hours per course per
week, with a central estimate of 1.3 (about 17 hours over a 13-week
semester); it is most sensitive to the question rate, the handling time, and
the share of questions that would otherwise have reached staff --- exactly
what logged chat turns would measure. It is an illustration under
assumptions, not a measurement.

A secondary, complementary signal, possible once chat turns are logged
(\autoref{concl:sec:limitations}), is question-topic clustering over the same
logs: the distribution of what students actually ask provides an objective,
behaviour-based teaching signal that complements student evaluations of
teaching, whose limitations (expected-grade bias, perceived rather than
actual learning) were noted in \autoref{review:subsec:quality}.

\subsection{Token, Cost, Latency, and Answer-Quality Metrics}
\label{eval:subsec:tokenmetrics}

The compression stage is evaluated on the comparison dimensions the
prompt-compression literature itself uses
(\autoref{review:subsec:compression}), so that the evaluation speaks the same
metric language as the problem statement
(\autoref{intro:sec:problem}) and the baseline token audit
(\autoref{design:subsec:tokenaudit}):

\begin{enumerate}[nosep]
  \item \textbf{Input tokens per query}, before versus after compression,
        reported with the compression ratio --- the direct measure of the
        token inflation identified in \autoref{review:subsec:tokens};
  \item \textbf{Cost per query and per student per semester}, computed from
        the hosted provider's per-token list prices; for locally hosted
        generation, where no per-token charge exists, latency and
        memory-residency effects are reported instead;
  \item \textbf{End-to-end latency} (retrieval $\rightarrow$ compression
        $\rightarrow$ generation), including the compression stage's own
        overhead --- compression adds an inference step, and its cost is
        reported rather than netted out, following the practice
        of~\citet{facl25:Jeong}~\cite{facl25:Jeong};
  \item \textbf{Answer quality} on course-material question answering, to
        measure whether compression degrades answers --- mirroring how
        \textsc{Recomp} and TCRA-LLM report the compression--quality
        trade-off~\cite{iclr24:Xu, femnlp23:Liu}.
\end{enumerate}

\subsection{Context Compression: Token Reduction and Latency}
\label{eval:sec:results:compression}

The compression stage of \autoref{impl:sec:compression} was evaluated end-to-end
against the uncompressed RAG baseline on the deployed stack: identical questions,
identical retrieved chunks, generation by Llama~3.2 at temperature~0, with prompt
and output token counts taken directly from the inference runtime
(\texttt{prompt\_eval\_count}). The probe used the ingested CS3241 (computer
graphics) corpus with two in-syllabus questions --- Q1 on shadow rays, Q2 on
ray--sphere intersection --- and one deliberately out-of-syllabus question (Q3, on
TCP congestion control), with compression parameters $\tau = 0.5$, $k = 6$.
\autoref{eval:tab:compression} summarises the results.

\begin{table}[htb]
  \centering
  \caption{Uncompressed RAG versus extractive compression ($\tau=0.5$, $k=6$) on
           the deployed system. Compressed latency includes the compression
           overhead itself (1.1--2.0\,s per query on the 8\,GB host).}
  \label{eval:tab:compression}
  \begin{tabular}{l r r r}
    \hline
    \textbf{Metric} & \textbf{Raw RAG} & \textbf{Compressed} & \textbf{Change} \\
    \hline
    Prompt tokens, Q1            & 769            & 257           & $-66.6\%$ \\
    Prompt tokens, Q2            & 545            & 195           & $-64.2\%$ \\
    Response tokens, Q1          & 354            & 122           & $-65.5\%$ \\
    Response tokens, Q2          & 91             & 86            & $-5.5\%$  \\
    End-to-end latency, Q1       & 17.2\,s        & 7.7\,s        & $-55\%$   \\
    End-to-end latency, Q2       & 5.7\,s         & 5.2\,s        & $-9\%$    \\
    Context retained (chars), Q1 & 100\%          & 26.9\%        & ---       \\
    Context retained (chars), Q2 & 100\%          & 18.7\%        & ---       \\
    Off-syllabus context, Q3     & $\sim$446 tok. & 0 (empty)     & ---       \\
    \hline
  \end{tabular}
\end{table}

Three observations follow. First, compression removed roughly two-thirds of the
prompt tokens on in-syllabus questions while retaining the sentences that answer
them (the top-scoring sentence for Q1 was the corpus sentence defining shadow
rays, at cosine similarity 0.66). Because a compute-bound local model's latency
scales with prompt length, this translated into a net end-to-end speed-up
despite the added compression step. Second, the shorter, more focused context
also changed generation behaviour: on Q1 the baseline produced a longer answer
that drifted into adjacent material, whereas the compressed run stayed on the
retrieved definition, consistent with the distraction effect reported
by~\citet{tacl24:Liu}~\cite{tacl24:Liu}. Third, selective augmentation behaved as
designed: for the out-of-syllabus Q3, every candidate sentence scored below
$\tau$ (0.40--0.42, against 0.57--0.82 for in-syllabus sentences), so no context
was injected and the model correctly reported the topic as outside the course
materials; at a looser $\tau = 0.4$ the same query leaked three marginal
sentences, illustrating that $\tau$ is the precision--recall control of the
stage.

Compression is not uniformly beneficial, however. On Q2 the sentence containing
the ray--sphere intersection \emph{equation} itself scored below the retention
cut-off, and the compressed answer, while correct about the discriminant, could
no longer reproduce the equation --- an answer-quality regression directly
attributable to over-compression. This mirrors the recall risk inherent to
extractive compression~\cite{iclr24:Xu} and motivates the conservative default
($\tau = 0.5$ with $k = 6$) and the per-deployment tunability noted in
\autoref{impl:sec:compression}. These results are indicative rather than
statistically robust: they derive from a three-question probe over a single
course corpus, and a larger question set across multiple courses is required
before the reductions can be claimed as general.

\subsection{Context Compression: Answer Quality}
\label{eval:sec:results:quality}

\autoref{eval:tab:quality} summarises the answer-quality evaluation of
\autoref{eval:subsec:setup:quality}.

\begin{table}[htb]
  \centering
  \caption{Answer quality with and without compression (IT5001, 20
           in-syllabus questions, gpt-oss-20b). Latency is generation only;
           compression adds its own overhead, reported in the text.}
  \label{eval:tab:quality}
  \begin{tabular}{l r r}
    \hline
    \textbf{Metric} & \textbf{Uncompressed} & \textbf{Compressed} \\
    \hline
    Mean correctness (0--2)          & 1.55   & 1.30   \\
    Fully correct                    & 65\%   & 55\%   \\
    Wrong or empty (score 0)         & 10\%   & 25\%   \\
    Draws on the course material     & 40\%   & 25\%   \\
    Prompt tokens (mean)             & 1\,693 & 789    \\
    Output tokens (mean)             & 221    & 234    \\
    Generation latency (mean)        & 0.84\,s & 0.72\,s \\
    \hline
  \end{tabular}
\end{table}

Compression cut the prompt by 53\%, keeping on average 4.5 of 23.4 candidate
sentences from the five retrieved chunks, and answer quality fell. Compared
question by question, the compressed answer was better on 3 questions, the
same on 10, and worse on 7; with 20 questions this difference is not
statistically significant (two-sided sign test, $p = 0.34$), but its
direction is consistent. Contrary to expectation, the loss was not
concentrated in the \emph{code} questions, whose mean score was unchanged
(1.2 in both conditions), but in the \emph{prose} questions (1.67 to 1.33).

Most of the loss came from the persona's Socratic behaviour rather than from
wrong answers. Seven answers in each condition were Socratic, but the
compressed ones were more often empty of content: five of seven compressed
Socratic answers stated no fact from the reference, against two of seven
uncompressed. Among the answers that did answer directly, all 13
uncompressed answers were fully correct, against 11 of 13 compressed. Both
compressed shortfalls had the same cause: the answer quoted a garbled sentence
``from the notes'', in which the compressor had removed the inline code ---
for example, a sentence recommending ``the module'' where the notes name the
\texttt{decimal} module.

Compression added its own latency. Embedding the candidate sentences, which
on the hybrid deployment travels to the local embedding host, took 4.0\,s on
average (1.1--20.3\,s), against a saving of 0.12\,s in generation. On this
deployment, compression therefore made answers slower, not faster, the
opposite of the compression probe, which ran on a compute-bound local model
whose generation time fell with prompt length.

For the four off-syllabus questions, the uncompressed condition injected
two to five irrelevant chunks: their nearest distances (0.48--0.59) overlap
the range of the in-syllabus questions (0.32--0.54), so the 0.6 cut-off cannot
separate them. Compression withheld all of them in every case, as selective
augmentation intends. Yet in neither condition did any answer say that the
course material did not cover the question (0 of 8): the assistant answered,
or asked questions, from general knowledge.

The two gpt-oss models were 1.5--6.6 times faster end to end than the local
models usable for production (Llama~3.2 and Qwen3 14B) and matched the best
of them on grounding (10/10). The only faster local model, Qwen3 8B, never
called the expected tools and grounded only 3/10 turns. Hosted throughput was 6--50 times
higher (475--965 against 19--75 tokens per second), and these latencies are
conservative: from the EC2 application server, an agent pass took
229--256\,ms.

Two further observations matter for the token argument of this thesis.
First, the hosted gpt-oss models took three passes per multi-part turn where
the local models took two, chaining the two tools sequentially; each pass
re-sends the full prompt, which is why their input-token counts are higher.
Second, the gpt-oss models always reason, and reasoning is billed as output:
at medium reasoning effort a quiz question consumed 400--650 reasoning tokens
against 10--50 at low effort, for equally valid output --- a hidden
output-token multiplier with no visible benefit, which is why the deployment
uses low effort.

\subsection{Cost per Query and per Student}
\label{eval:subsec:results:cost}

The benchmark prompts carry no retrieved context, so production cost is
modelled by adding about 1\,000 tokens of retrieved context per pass --- an
upper-range assumption, since the token audit measured about 510 tokens on
the CS3241 corpus (\autoref{design:subsec:tokenaudit}) --- with
and without the 65\% reduction measured in the compression probe
(\autoref{eval:sec:results:compression}). Costs use Groq's list prices
(gpt-oss-20b: US\$0.075 input and US\$0.30 output per million tokens;
gpt-oss-120b: US\$0.15 and US\$0.60; retrieved 27 September 2026). The
per-semester projection assumes 20 chat turns, 10 quiz questions, and one
quiz-feedback note per student per week over 13 weeks. These are
round-number assumptions, not measured usage.

\begin{table}[htb]
  \centering
  \caption{Projected generation cost per student per semester (US\$).}
  \label{eval:tab:cost}
  \footnotesize
  \begin{tabular}{l r r r}
    \hline
    \textbf{Model split} & \textbf{No retrieval} & \textbf{+ RAG}
      & \textbf{+ RAG + compression} \\
    \hline
    Agent 20b, quiz 120b (deployed) & 0.090 & 0.148 & 0.110 \\
    Agent 120b, quiz 20b            & 0.141 & 0.258 & 0.182 \\
    All 120b                        & 0.152 & 0.269 & 0.193 \\
    \hline
  \end{tabular}
\end{table}

With retrieved context included, projected cost is US\$0.11--0.27 per
student per semester, against the US\$7.50 per student per course per
semester reported for Ethel~\cite{tpt24:Kortemeyer}. The comparison is
indicative only: Ethel used a different model class, different usage
patterns, and 2024 pricing, and a single institution's figure should not be
read as a general benchmark.

The agent loop adds a mechanism the literature reviewed in
\autoref{review:subsec:tokens} does not isolate: \emph{tool use multiplies the
prompt}. Each pass re-sends the system prompt, the retrieved context, and the
tool schemas, so context injected once per turn is billed once per pass ---
three times on the multi-part turn. Compressing a 1\,000-token context by
65\% therefore cuts the cost of a gpt-oss-20b agent turn by about 30\%
(US\$0.00049 to US\$0.00034), more than the same compression saves in
single-pass RAG. Token counts are not comparable across model families ---
the same prompt counted 1\,093 tokens under Llama~3.2, 758 under Qwen3, and
672 under gpt-oss --- so compression ratios are compared within a model only.

Separately, the free tier's 8\,000 tokens per minute per model serve only
about 1.4 agent turns per minute, so course-scale use needs a paid tier.

\section{Discussion}
\label{eval:sec:discussion}

\paragraph{RQ1: measuring instructor time.} The measure of
\autoref{eval:subsec:hours} is simple and deliberately conservative, and it
can be computed directly from the assistant's own records --- provided those
records exist. The deployed system does not yet store chat turns, so the
measure could not be applied. The lesson is a design one: what an assistant
stores decides what can later be claimed about it, so the data a workload
measure needs should be specified, as here, before deployment rather than
after.

\paragraph{RQ2: compression.} Extractive compression reliably cuts input
tokens: by about two-thirds in the probe and by 53\% on the IT5001 question
set. Its other effects depend on the deployment and on the question. On a
compute-bound local model it cut end-to-end latency, but on the hybrid
deployment its own embedding step, which runs on the remote embedding host,
cost far more than it saved, so answers became slower. Its cost to quality,
measured on 20 questions, was small for questions the model answered
directly, but real overall: mean correctness fell from 1.55 to 1.30 and wrong
or empty answers rose from 10\% to 25\%, mostly because, with less context,
the Socratic persona more often replied with questions that conveyed nothing.
Removing code also produced garbled quotations attributed to the notes. On
the other side, compression kept irrelevant material out of every
off-syllabus prompt, which the distance cut-off alone did not. Compression is
therefore worth keeping as an option rather than as a default: it suits
deployments where generation is compute-bound and embedding is cheap, and it
needs to preserve code before it suits course material like IT5001's. Its
reach is also bounded: on the deployed agent, retrieved context is only about a fifth of
the first-pass prompt, behind the tool definitions and the system prompt
(\autoref{design:subsec:tokenaudit}), so compression alone cannot cut the
prompt by more than that share.

\paragraph{RQ3: deployment model.} Hosted generation was faster than every
local model usable in production, equally grounded, and more often correct
on quiz answer keys, at a projected cost of cents per student per semester.
Retrieval could not move to the hosted provider, and a local fallback turns
provider failures into degraded answers rather than outages, so the hybrid
model best meets the requirements.

\paragraph{Tokens as the cost lever.} Both regimes reward fewer input tokens
--- billed and multiplied by agent passes when hosted, and paid in prefill
latency and memory pressure when local --- supporting the claim of
\autoref{intro:sec:problem}.

\paragraph{Threats to validity of the provider benchmark.}
Samples are small ($n=10$ and $n=3$): enough to rank models, not to support
P95 latencies. Local and hosted runs were five weeks apart, on different
Ollama versions, with identical prompts, stubs, and loop; hosted latencies
include trans-Pacific round trips and exclude free-tier throttling. Quiz
correctness was judged by an AI model in one unblinded pass, which may share
failure modes with the models it rated. Stubbed tools measure model
behaviour, not live-data effects, and no complete production turn was timed
on the hosted provider. The cost projection rests on assumed usage rates.

\paragraph{Threats to validity of the answer-quality evaluation.}
The evaluation uses 20 in-syllabus questions from one course, scored by one
rater, so it shows the direction of the effect, not its size with any
precision; a larger, multi-rater question set is needed. Blinding was
imperfect: the two garbled quotations reveal which condition produced them.
The Socratic persona confounds the measure, since an answer that withholds a
correct explanation by design scores the same as a wrong one; a variant of
the evaluation that asks the persona for a direct answer would separate the
two. Answers were generated without tools and at temperature~0, which
isolates the effect of the context but differs from production, where the
agent may call tools.

\section{Summary}
\label{eval:sec:summary}

For RQ1, the thesis defines an hour-denominated measure of the instructor
time the assistant returns, and identifies that computing it requires
stored chat turns, which the deployed system does not yet keep; an
illustrative projection puts it at 0.1--7.2 hours per course per week
(central estimate 1.3). For RQ2, extractive
compression cut input tokens by 53--67\% and kept irrelevant material out of
off-syllabus prompts, but on 20 IT5001 questions it lowered mean answer
correctness from 1.55 to 1.30 (not statistically significant), largely
through content-free Socratic replies, and on the hybrid deployment its
embedding step made answers about 4\,s slower. For
RQ3, a hybrid deployment --- hosted generation, local retrieval, and a local
fallback --- was faster than the local alternatives at equal grounding, at a
projected US\$0.11--0.27 per student per semester. Both results come from
small samples and need larger question sets.
